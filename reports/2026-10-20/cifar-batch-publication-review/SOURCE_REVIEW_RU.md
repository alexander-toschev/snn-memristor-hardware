# Проверка обёртки конечной партии CIFAR

Вердикт: исходники `tools/run_cifar_batch.py` пригодны для публикации и
предварительной проверки на Raspberry. После неё основной оператор может
использовать обёртку с уже проверенным конечным планом stages19…24.
Обёртка не меняет физический протокол, не продлевает план автоматически и
не заменяет последующий локальный raw-аудит. Аппаратных вызовов при этом
review не было.

Обёртка запускает неизменённый `experiment.py` foreground. Его собственные
проверки источников/INI/grant и MemriBoard Connector остаются единственным
путём аппаратного ввода-вывода. После завершения child она отдельно проверяет
принадлежность новых UUID плану, final inventory или явно отмечает отсутствие
final у завершившегося child. Неясный статус и аппаратный lock блокируют
публикацию; файлы остаются на месте. `finalize` и повтор push никогда не
повторяют воздействия на плату.

Проверены точный список файлов и отказ от symlink/reparse, исходные и
декодированные gzip-потоки при поиске секретов, сканирование метаданных,
LFS pointers и соответствие их SHA/размера сохранённым байтам. Повреждённый
или не полностью проверяемый поток не выдаётся за успешно просканированный.
Допускаемый усечённый gzip сохраняется в исходном виде с явным статусом.

Все пять штатных hooks закреплены SHA, неожиданные hook-файлы запрещены.
Git явно использует `.githooks`; hooks не обходятся. Исправлено наследование
`GIT_LFS_SKIP_PUSH`, а `lfs.allowincompletepush=false` задан явно.
На незафиксированном повторе сканируются заново все файлы; метаданные
публикации привязаны к исходному batch, exit, сессиям, версии обёртки и
назначению push. После собственного commit повтор проверяет точный parent,
список и байты и отправляет тот же commit. Другой HEAD/индекс блокирует путь.

Push допускается только в заданный GitHub-репозиторий и ветку
`codex/full-cifar-diagnostic`, без force. Используется существующий
неинтерактивный credential cache; файлы с секретами не читаются. Произвольный
вывод native/Git/сканера не выводится в статусы. Подтверждение remote ref и
успех стандартного pre-push не называются отдельным скачиванием и проверкой
удалённых LFS-объектов.

Независимая проверка покрыла все18 тестов. Семнадцать synthetic/mocked
проверок прошли в sandbox. Изолированный Git/LFS integration test сначала
упёрся в ограничение Windows sandbox для Git filter; затем отдельно прошёл
с разрешённым запуском вне sandbox:1/1 за6,409с. Он создаёт одноразовый
репозиторий, проверяет отказ hook, повтор commit без повторного acquisition,
тот же commit при повторе и настоящий LFS pointer. Hooks и сканер в этом
тесте — заглушки. Git проекта, сеть и плата не изменялись. Первое обращение
к системному TEMP также было заблокировано средой; повтор использовал
repo-local `.tmp`. Это не ошибка acquisition и не доказательство работы
реального Gitleaks/credential cache на Pi.

До запуска остаются обычные проверки на Pi: опубликованная версия кода,
clean tracked состояние и индекс, наличие Git LFS/Gitleaks/штатных hooks,
точный план и grant, отсутствие чужого lock. Потеря всего терминального
процесса не гарантирует выполнение автокоммита; после восстановления связи
нужен разбор и явный `finalize`. Сбой публикации не разрешает следующий
аппаратный batch автоматически.

Статусы acquisition, committed, pushed и semantic audit различаются.
Ни успешная публикация, ни этот review не означают завершения48 stages,
правильных весов или точности CIFAR.
