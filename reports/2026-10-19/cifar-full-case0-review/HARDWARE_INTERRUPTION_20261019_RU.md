## Сохранение исходных свидетельств

Root сначала сохраняет и публикует исходные bytes через Git LFS, до любой
попытки продолжения. Нельзя обрезать/дописывать последний gzip, пересоздавать
original index/manifest, дописывать фиктивный session_complete или заменять
status на completed. Не удалять lock, не перезапускать опыт и не обращаться
к плате в рамках этого разбора.

Отдельный preservation inventory вне исходной сессии должен содержать:

- точные относительные имена, размеры и SHA256 всех имеющихся файлов;
- SHA/содержимое start_manifest, protocol, INI и привязку к source commit;
- копию/хеш текущего lock как свидетельство, время наблюдения и результаты
  read-only process checks; lock не включать в исполняемый resumed checkout;
- статус каждого gzip: CRC/EOF, число полных JSONL-строк, последний полный
  event/task/stage и наличие незавершённого request/result;
- для оборванного потока — точную границу восстановленных полных строк и
  отдельно сохранённые trailing bytes. Это производный diagnostic artifact,
  не исправление оригинала и не новый валидный original gzip.

Тяжёлое распаковывание, проверка и prefix replay выполняются локально после
переноса; Pi оставляем для acquisition и необходимой публикации. Нельзя
объявлять сохранённые файлы прошедшими strict audit лишь по успешному push.

## Что действительно является checkpoint в frozen коде

В `collector.py` событие называется **`stage_complete`**, не stage_end.
Оно испускается после программирования тайла, новой калибровки/heldout,
всех784 spatial positions со всемиT12 входами и полного final_basis.
`position_complete` отдельно не квалифицирует весь тайл.

`trace.Writer` закрывает завершённый gzip при ротации; индекс всего потока
пишется только в `finish()`. Entry пишет финальный manifest после возврата
из collector/finally. Поэтому отсутствие manifest и оборванная gzip-часть
не позволяют предполагать штатное прохождение этих финальных проверок.
Текущий `audit_native.py` требует48 stages, `session_complete` и полное
покрытие тензора; существующий classifier также требует completed manifest.
**Встроенного resume/range CLI у frozen acquisition нет.** Повтор обычного
`--run-hardware --scope full` начинает новый полный опыт с stage0.

Stage13 в raw — индекс с нуля, то есть14-й этап. Stages0…12 являются только
кандидатами на сохранённый prefix. Они ещё не подтверждены независимым аудитом.
Если все13 пройдут проверку, первые12 этапов покрывают фильтры0…15 полностью,
stage12 — первые32 taps фильтров16…19. Это не полный CIFAR-классификатор.

## Проект безопасного продолжения — ещё не реализован и не допущен

1. **Отдельный локальный prefix auditor.** Проверить source/INI/case/checkpoint
   identity, порядок request/result, native responses, guards, все programming
   evidence, fit/selection/heldout, frozen C, position coverage и final_basis.
   Принимать только непрерывный prefix целых stages с фактическим
   `stage_complete` и без открытой операции. Не подсовывать старому полному
   аудитору искусственный footer или изменённый scope. Сохранять task IDs и
   ссылки на исходные byte ranges.
2. **По умолчанию опираться на целые gzip-части с проверенным CRC/EOF.**
   Незавершённый part сохраняется как diagnostic evidence. Даже полные строки
   внутри него не имеют валидного завершающего gzip CRC; использование такого
   tail для допуска stage требует отдельного решения по целостности.
   Принятый prefix может содержать меньше13 этапов — заранее его не выбирать.
3. **Новая отдельная reviewed continuation-сессия/entry.** Начать с первого
   непринятого stage целиком: fresh bounded RESET/SET этого тайла, fresh nativeR
   guards, новая basis/fit/selection/heldout и новый C. Затем все784 positions
   и final_basis. Не продолжать с последней позиции, task4193827 или старой C;
   текущее физическое состояние нельзя выводить из оборванного result.
4. **Новый конечный бюджет заранее.** Если принят prefix0…12, новые этапы13…47
   составят35 stages. Число допустимых impact/импульсов следует пересчитать
   по точным range/schedule до запуска; исторические попытки, включая потерянный
   хвост, не обнулять в общем отчёте. Не выдавать это за новый полный прогон
   от одинакового начального состояния. Нужны offline tests/native SIM/review
   для новой ветки продолжения; frozen исходники первого прогона не менять.
5. **Отдельная проверка объединения.** Ровно один принятый источник каждого
   stage, без пропусков/дубликатов/CPU fill. Хранить mapping
   `(stage → session UUID → source SHA → calibration SHA → payload SHA)`.
   Суммировать три тайла до checkpoint BN/LIF один раз на логический timestep.
   Итог явно называется composite interrupted+continuation result, содержит
   оба времени/состояния/протокола и не переписывает исходные manifest.
6. **Аппаратный допуск root отдельно.** Сначала выяснить владельца lock и
   подтвердить отсутствие других операторов/процессов, сохранить свидетельства
   инцидента и согласовать освобождение. Нынешний документ не разрешает удаление
   lock, закрытие/сброс платы или запись. Все реальные операции только public
   MemriBoard Connector/native converters/INI, команды foreground, без detach.

Локальный перенос проверки private MemriCORE SHA и платформенных rank7/C чисел
также остаётся отдельным незавершённым условием. Его нельзя обойти ради resume.
Если сохранённый prefix не удаётся квалифицировать, честный результат —
прерванный опыт с диагностическими данными; новый полный/сокращённый опыт
обсуждается отдельно, без выдачи диагностического tail за полноценный inference.

### Уточнение границ доказательства

Счётчик независимо проверенных операций является **нижней границей**, а не
точным числом всех фактических impact: неизвестный буферизованный или оборванный
хвост не оценён. Сохранённый `stage_complete` подтверждает собственное окно
измерений этого тайла; его final_basis не доказывает текущую проводимость после
записей следующих тайлов, простоя и разрыва сессии. Composite может содержать
измерения разных временных окон, что должно сохраняться в provenance.
