# MNIST128: пилот завершён, данные проверены

**PASS для целостности, повторяемости и работоспособности извлечения признаков на этих 128 train-примерах.** Оба прохода дали побайтно одинаковые counts; все примеры вызвали спайки. Можно готовить полное извлечение train-признаков отдельным ограниченным сценарием с теми же весами, окружением и сбросом состояния. Это не результат классификации: readout не обучался, test split не использовался, точность 69,65% не воспроизведена.

**Уточнение цели после пилота:** пользователь запросил повтор именно STDP-обучения MNIST. Поэтому этот результат остаётся smoke окружения и извлечения признаков; он не выполняет целевое задание обучения. Нижеприведённые оценки полного frozen-feature extraction — технические свойства проверенного режима, не утверждённый следующий этап. Для STDP-training нужны отдельные восстановленный протокол, исходная инициализация, ограниченный бюджет и проверка изменения весов.

## Границы доказательства

Сохранён один входной spike-тензор, для прохода 0. Равенство входа прохода 1 подтверждено проверкой внутри замороженного runtime и одинаковыми per-pass SHA; второго самостоятельного файла для независимого сравнения нет. Оба **выходных counts** сохранены и сравнены непосредственно.

Сохранённый `frozen_weights.npy` содержит checkpoint-веса. Неизменность live weights/thresholds/bias подтверждается runtime-проверками и per-pass SHA, но отдельные конечные live-тензоры и полный временной выходной spike-поток не сохранены. Аудит не переисполнял Conv/LIF и не является независимым численным forward-сравнением. В будущем расширенном сборе желательно сохранять final-state hashes явными отдельными полями и исходный commit/dirty status в manifest.

Основной оператор сообщил clean tracked runtime `c9d39ed4cd854c529f01806d05afb256b3e49230`; такой commit существует, однако сам manifest этого пилота не содержит git commit/dirty status. Поэтому это операторская provenance-запись, отдельно от непосредственно проверенных source hashes.

Остаются ограничения [source review](SCIENTIFIC_REVIEW_RU.md): новая реконструкция с `learning=False`, сохранённый неработающий post-window E/I hook, неаттестованное историческое окружение, стандартная задержка Input→Conv1 на один шаг. В последнем входном timestep было 22 спайка; при этом расписании они не достигают Conv1 до конца T=100. Дополнительный timestep после просмотра результата не добавлялся. Нельзя называть эту реализацию исправленным E/I или утверждать воспроизведение исторической accuracy.

## Переход к полному извлечению

Технического блокера, обнаруженного на данном пилоте, нет: CUDA forward завершился, features не молчат, checkpoint сохранён, повторяемость точная. Следующий сценарий должен закрепить выбор train IDs, chunk/batch 128, обработку последнего неполного batch, reset между batch, то же deterministic кодирование и семантику задержки; сохранять counts частями с хешами и возобновлением без дублирования/пропусков. Не удерживать весь временной monitor для большого датасета. Текущий пилот не расширять скрытой заменой списка IDs.

Один float32-массив counts для 40 000 примеров займёт около 5,49 GiB, для 60 000 — 8,24 GiB, без дополнительных копий/readout-нормировки. Это прямой расчёт формы, не измерение полного задания. Линейное умножение двух наблюдавшихся времён даёт около 26–45 минут на 40 000 примеров при том же batch и одном проходе; это лишь начальный ориентир, **не гарантированный ETA**: ещё не проверены устойчивость длительного сбора, дисковые расходы и последний batch. После извлечения понадобится отдельное train-only обучение/фиксация readout и его нормировки, затем независимая test-оценка. Пока accuracy отсутствует.
