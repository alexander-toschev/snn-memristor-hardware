# Разработчику MemriBoard: запуск и разбор результатов

Команды ниже выполняются на Raspberry Pi из клонированного репозитория.
Это инструкция для отдельного запуска оператором, а не автоматическое продолжение
эксперимента. Полная калибровка выполняет RESET/SET по всем 256 адресам
WL0–7 × BL0–31 и **изменяет состояния массива**, включая WL1.

## Код, окружение и проверка без подключения

Подготовка `.venv`, зависимости и копирование двух приватных файлов штатного
драйвера с проверкой SHA описаны в [REPRODUCE.md](REPRODUCE.md), раздел
«Окружение и локальный драйвер». Эти файлы не публикуются в GitHub. Здесь
используется `.venv/bin/python` именно из репозитория. На плате не должно быть
другого приложения, одновременно управляющего тем же оборудованием.

```sh
cd ~/Documents/snn-memristor-hardware
git status --short
git switch main
git pull --ff-only origin main
git rev-parse HEAD
.venv/bin/python experiment.py --dry-run --calibrate-cells
```

При конфликте веток или локальных правках остановитесь и разберите различия;
не используйте reset/clean для обновления. Сохраните SHA показанного коммита.
Dry-run проверяет сохранённые исходники, INI, конфигурацию и пределы сценария;
он не открывает Connector, не проверяет импортируемость всех зависимостей
и не доказывает правильность подключения платы.

## Полная калибровка — отдельная изменяющая массив команда

**Проверка тока v2:** `gui/windows/apply.py:515–525` перед mode7 вычисляет
`current_predict = vol / resistance_previous` и пропускает запись при sign0 >0.04 А
или sign1 >`man.soft_cc` (в данном INI 0.002 А). Текущий протокол
`cell-conductance-discovery-v2-gui-write-guard` использует ту же формулу,
пороги и разрешённое равенство для валидного последнего native R mode7 данной
ячейки. MVM не меняет этот R. Пропуск журналируется без impact, ADC и изменения q,
а лестница продолжает следующий шаг. Счётчики решений, пропусков и реальных
попыток импульса разделены. Отличие сохраняется для невалидного R: остановка,
без GUI-подстановки epsilon вместо нуля.

Историческая сессия `f32eab10-9abd-4d8c-a4c5-3ed49a3cb8fb` выполнялась по v1
**без** per-pulse current guard. Её данные и описание не переписаны задним числом.
Следующая команда воспроизводит **наш текущий v2 протокол**, а не полностью GUI.
Для первичной сверки ниже приведён отдельный read-only сценарий.

```sh
.venv/bin/python experiment.py --run-hardware --calibrate-cells
```

Параметры находятся в [configs/cell_calibration.json](configs/cell_calibration.json),
сценарий — в [cell_calibration.py](cell_calibration.py), описание —
в [CELL_CALIBRATION.md](CELL_CALIBRATION.md). Это один bounded discovery cycle:
mode7 readback, RESET/SET 0.3…3 В с шагом 0.01, checkpoint при пересечении q-порогов,
mode10 на одиночном BL с zero/.025/.05/.075/.1/zero и начальное/финальное чтение
всего массива. Максимум 138 752 решения о записи (включая skips), не более
138 752 реальных попыток ненулевой команды и 203 008 impacts.
Все обращения идут через публичные `Connector.open_port/impact/close_port`.
Native converters используются без подмены ADC; измерения не являются
калиброванными физическими напряжениями/токами.

В конце программа печатает JSON вида
`{"session":"results/cell_calibrations/<новый UUID>","status":"completed"}`.
Скопируйте **session из вывода именно этой команды**; не выбирайте последний
каталог по дате и не подставляйте прежний UUID. `failed` и ненулевой exit code
требуют разбора сохранённой ошибки, а не автоматического повторного запуска.
При аварийном завершении до финального JSON сначала найдите относящийся к этому
запуску `start_manifest.json` по времени/коммиту; не анализируйте случайную старую сессию.

## Аудит и отчёт новой сессии — без аппаратуры

Замените `UUID_FROM_FINAL_JSON` значением из финального сообщения выше:

```sh
CAL_SESSION='results/cell_calibrations/UUID_FROM_FINAL_JSON'
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
.venv/bin/python audit_calibration_generic.py --repo . --session "$CAL_SESSION" --output-dir "$CAL_SESSION/offline-audit-$STAMP"
.venv/bin/python render_cell_calibration.py --repo . --session "$CAL_SESSION" --output "$CAL_SESSION/report-$STAMP"
```

Новые выходные каталоги сохраняют предыдущие отчёты. Сначала проверьте
`audit_status`, `errors` и статус сбора. `report-.../index.html` открывается локально
в браузере; рядом находятся `cells.csv`, `states.csv`, `calibration.json`.
Исторически удачное состояние не означает, что оно осталось на плате после
дальнейших записей. Отчёт не экспортирует готовую маску для CIFAR.

## Существующие результаты: точные команды offline

Аппаратная calibration-сессия уже существует на исходной Raspberry. Для полного
повторного аудита нужны все её оригинальные файлы, включая raw, checkpoints и
summary, а также соответствующие исходники и приватные драйверы. В публичном Git
лежит компактный снимок этой сессии; одного clone недостаточно для этих двух команд.
Сначала получите полный каталог у оператора, сверив hashes из manifest.

```sh
CAL_SESSION='results/cell_calibrations/f32eab10-9abd-4d8c-a4c5-3ed49a3cb8fb'
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
.venv/bin/python audit_calibration_generic.py --repo . --session "$CAL_SESSION" --output-dir "$CAL_SESSION/offline-recheck-$STAMP"
.venv/bin/python render_cell_calibration.py --repo . --session "$CAL_SESSION" --output "$CAL_SESSION/report-recheck-$STAMP"
```

Полная новая карта после SET/RESET опубликована с raw и проверяется отдельно:

```sh
MAP_SESSION='results/cell_maps/26622224-338b-453e-a527-c2828e7f7a25'
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
.venv/bin/python audit_cell_map.py --source-repo . --session "$MAP_SESSION" --output-dir "$MAP_SESSION/offline-recheck-$STAMP"
```

Аудит также проверяет источники: используйте файлы, совпадающие с manifest сессии.
Несовпадение SHA не исправляется ослаблением проверки. Числовые результаты и ссылки:
[CALIBRATION_RESULTS_20261015.md](CALIBRATION_RESULTS_20261015.md).

## Новая карта текущего состояния — отдельный read-only запуск

Это другая команда, **не часть offline-разбора и не запускается автоматически**.
Она выполняет физические чтения mode9/mode10 всех 256 ячеек, без RESET/SET/mode7:

```sh
.venv/bin/python experiment.py --dry-run --map-cells
.venv/bin/python experiment.py --run-hardware --map-cells
```

Её финальный JSON даёт новый `results/cell_maps/<UUID>`. Подставьте его в
`MAP_SESSION` для аудита выше. Карта относится к состоянию на момент этого чтения.

## Что требуется сверить с приложением MemriBoard

Для первичной сверки без программирования можно отдельно выбрать сценарий
порядка MatMul: mode9 readback и mode10 на существующих проводимостях,
включая плотный вход всех 32 BL; RESET/SET не выполняются. Команды ниже —
инструкция оператору, не предложение автоматически запускать плату сейчас:

```sh
.venv/bin/python experiment.py --dry-run --check-mvm-gui
.venv/bin/python experiment.py --run-hardware --check-mvm-gui
```

Мы используем штатный Connector и converters, но это само по себе не доказывает
эквивалентность последовательности GUI. Сопоставлять нужно конкретные команды,
INI, DAC/ADC, маски и порядок WL/BL; заключение о полной GUI-эквивалентности
здесь не сделано.

Существенные отличия сценария, несмотря на совпадающий write guard для валидного R:

- GUI `math.py:1201–1217` при prediction≥`vol_comp` (3.3 В) пропускает impact
  и подставляет ADC0. Калибровка при нарушении модельных/наблюдаемых guards
  останавливается; её сохранённый raw ADC0 — ответ Connector, не GUI skip.
  Применяется также граница 80% ADC reference для измеренного выхода.
- GUI MatMul обходит входные векторы, затем WL. Калибровка обходит ячейки и
  состояния, подавая один BL≤0.1 В; RESET/q-target/checkpoints — наш отдельный
  алгоритм, а не встроенная процедура GUI.
- GUI передаёт длительность из задания; аппаратная калибровка передаёт 0.
  Проверенная физическая реализация mode7 игнорирует эти timing-параметры.

Таким образом, одинаковая форма native-команды не означает одинаковый алгоритм.

На Raspberry непосредственно сверены SHA256 восьми существующих исходников
между `~/Documents/MemriBoard` и `vendor/MemriBoard` этого репозитория; все восемь
совпали: `manager/board.py`, `manager/service/converters.py`,
`manager/modes/std.py`, `manager/blanks.py`, `gui/windows/math.py`, `gui/windows/apply.py`,
`MemriCORE/rp5_fpga_python/rpi_FPGAed.py`, `MemriCORE/rp5_fpga_python/FPGA_SIM.py`.
`main.py` отсутствует в обоих расположениях и не учитывается как совпавший файл.
Это проверка одинаковых байтов, а не одинаковых последовательностей вызовов.
Также на Pi сравнены словари секции `[board]` установленного
`../MemriBoard/settings.ini` и `configs/raspberry_board.ini`: полное совпадение,
список различий пуст. Это не утверждение о совпадении остальных секций INI.

1. В обеих картах, включая карту **до** нынешнего SET/RESET, прямоугольник BL16–30
   на всех восьми WL даёт нулевой MVM-отклик. В новой карте это 1200 mode10 ADC=0,
   тогда как 720 mode9 чтений тех же 120 адресов валидны, ADC105…2238.
   Соответствуют ли выбор банка/BL, адресация WL, коммутация и путь измерения mode10
   ожидаемому поведению приложения? Нули не доказывают неисправность мемристоров.
   В исходнике `mode_mvm` маска строится по 32 условиям input>0, затем передаётся
   четырьмя группами по 8 с индексом `j+8*i` и `mvm_css=[13,19,26,21]`.
   Это наблюдение о коде; реальное соответствие линий платы логическим BL
   независимо не подтверждено.
2. В проверенной версии физического `mode_7(vDAC,tms,tus,...)` параметры tms/tus
   не используются для выдержки импульса. Какова предусмотренная длительность
   в этой версии и как приложение её задаёт? В отчётах длительность отмечена
   неизвестной; 125 мкс относится только к модельному сценарию simulator.
3. В v2 guard использует последний успешный mode7 `result[0]` и сохраняет skipped
   команды отдельно; mode10 не подменяет этот R. Верно ли это отражает намерение
   GUI-проверки при вставленных MVM checkpoint? Нулевой/невалидный R останавливает
   сценарий. Совпадение формулы guard не подтверждает эквивалентность всего алгоритма.

Для сверки передайте публичный код, commit из manifest, INI/протокол и журналы
команд/ответов нужной сессии. Приватные исходники драйвера передаются только
оператором по согласованному каналу; не добавляйте их в GitHub.
